# How to refute something here

This repository is a set of conjectures written to be knocked down. Disagreement isn't
tolerated here, it's the product. If you think a note is wrong, you are the reader it was
written for.

What follows is not etiquette. It's a map of where the notes are weakest, so you don't
have to hunt for it.

## Where to aim

**Start with "What would change my mind."** Every note ends its *Where it stands* section
with a list of conditions under which I would abandon or revise the position. That list is
not decoration — it is the note telling you exactly where it is load-bearing. If you can
meet one of those conditions, you have refuted the note by its own stated standard, and
there is nothing left for me to argue about.

**Then read the Sources section.** Where a note leans on checkable facts, it carries one.
Two things in there are targets:

- Anything marked **NOT VERIFIED** — a claim I could not confirm and chose to flag rather
  than delete. If you can confirm or destroy it, that is immediately useful.
- The **withdrawn** items — claims I abandoned, with reasons. If you think I withdrew one
  too readily, say so. Retractions can be wrong too.

**And read the status line.** Each note carries two dates: when the prose last changed,
and when its factual claims were last checked. If the second date is old, assume rot. A
note can go stale without a single word of it becoming false, and pointing at a claim that
has quietly expired is as valuable as pointing at one that was never true.

## What helps most

Roughly in order of how much it would change things:

1. **A factual correction with a source.** This has moved these notes more than any
   argument has. Errors found this way have included an inscription described as being
   somewhere it hasn't been since 1890, a settlement timescale off by two orders of
   magnitude, and a philosopher's argument stated backwards. A source beats an assertion
   every time — and a source I can actually open beats a citation I have to trust.
2. **"That is not what I believe."** Where a note describes a position — religious,
   philosophical, political — and describes it wrongly, tell me. This is the one failure
   mode I structurally cannot catch, because I wrote both the position and the objections
   to it. See the README section on who wrote the objections.
3. **An argument the note never considers.** Not a stronger version of an objection
   already there — a different one entirely.
4. **A motivated step.** A place where the reasoning survives only because I wanted the
   conclusion. The notes flag some of these against themselves; they cannot flag the ones
   I haven't noticed.
5. **A claim that has gone stale.** Newer data, superseded modelling, a question that has
   since been answered.

## What is less useful

Not unwelcome — just predictable, and usually already handled:

- **Disagreeing with a declared metric.** Where a note assesses something against a stated
  standard, it says so openly and admits the standard is a choice. Arguing that the
  standard is wrong is a real argument, but it is a different one, and the note has
  already conceded that it isn't neutral.
- **Restating an objection the note already makes.** Check *Refutations & tensions* first;
  it may be there, and if it is, the interesting move is to argue it isn't answered well
  enough.
- **General disagreement without a target.** "This is wrong" is not actionable. "This
  sentence is wrong, here is why" is.

## What happens to a good objection

It goes into the note, with credit. That is the convention this project runs on: when
someone who disagrees reads a note, that gets recorded *in the text* rather than used to
quietly retire an admission. A list of who pushed back and where is more informative than
its absence.

Concretely: I would rather add a paragraph saying "X argued this and they are right, so
the conclusion above is now weaker" than silently edit the conclusion. The revision
history is the point. If you look through the commits you will find several of these
already — arguments dying in public, which is what the repository is for.

## How

An issue is fine, and is the better choice if you want to argue before anything changes. A
pull request is welcome too, especially for factual corrections with sources.

Corrections require no ceremony and no hedging. You do not need to soften it.
